# Fix: card detail 404 on /api/cards/<uuid> — client opens detail with a media-object id

## Goal

Stop the card-detail modal from being opened with a media-object id (which can
never exist in `Cards.id`), so clicking a card never logs a 404 on
`/api/cards/...` again.

## Current context (traced, verified in code this session)

- Symptom: dev app (`:5173`) console shows `GET /api/cards/1ed9bc3a-b484-4536-b659-4873a4140b18 -> 404`.
  vite proxies `^/api` to central `https://gmatch.fly.dev` (`apps/desktop/vite.config.ts:118-124`),
  so this 404 came from the central node's real DB, not a local/stale process.
- The route is honest: `apps/api/src/routes/cards.ts:66-70` -> `CardService.getCard`
  (`apps/api/src/cards.ts:351-367`) does `SELECT ... FROM Cards WHERE c.id = ?`;
  404 = no canonical card row with that id (or a non-active card the caller doesn't own).
- Where a non-card id gets into that GET: the global card modal. Any tile dispatches
  `gmatch:open-card` via `openCardDetail(card)`
  (`apps/desktop/src/utils/openCard.ts:14-17`), which resolves the id with
  `canonicalCardId(card) = card.card_id || card.id` — **it silently falls back to the
  media-object id when the item has no canonical card**. App.tsx:959-966 receives the id
  and mounts `CardDetailView` which GETs `/api/cards/<id>` (CardDetailView.tsx:71) -> 404.
- That fallback fires for real items: `mergeMyCards`
  (`apps/desktop/src/utils/cardCollection.ts:198-204`) appends **legacy keepsakes
  (Objects with no canonical card) with `id = <object uuid>` and NO `card_id`**, and the
  two openCardDetail call sites render exactly those merged lists:
  - `DeckBuilder.tsx:445,488` (deck + available grids over `cards` = merged list),
  - `LobbyPanel.tsx:564` (`myCards` = deck-filtered merged list).
  The gallery path already guards this correctly (`GalleryView.tsx:377-378`:
  `const cardId = cardByMedia?.get(item.id); if (cardId) ...`) — the modal opener just
  never got the same rule.
- A UUID-vs-UUID detail: `Cards.id` is also a full UUID (`cards.ts:235`), so the shape of
  `1ed9bc3a-...` proves nothing either way; the client-side fallback is the only code
  path that systematically requests ids that cannot exist. (DeckBuilder's local
  `canonicalId()` at line 68 keeps its media-id fallback for deck membership — that is
  correct there, decks store media ids for legacy items; do NOT touch it.)

## Architecture / proposed approach

Root-cause fix in the one shared function: `openCardDetail` dispatches ONLY when the
item carries a real canonical `card_id`; no id, no modal (single-click on a legacy
keepsake becomes a no-op, exactly like the gallery; double-click zoom still works).
Delete the now-dead `canonicalCardId` helper (its only non-test consumer was this
fallback). No server change — the 404 was the server being honest.

### Task 2 — GREEN: guard + delete dead helper (2 min)

Replace `src/utils/openCard.ts` with:

```ts
/**
 * Ask the root CardDetailView host to open a card's full info modal (plan §12).
 * Only canonical cards have a detail endpoint: legacy keepsakes (media Objects
 * without a Cards row) must NOT open it — GET /api/cards/<media-id> 404s
 * (the gallery path has guarded this all along; DeckBuilder/LobbyPanel route
 * through here, so the guard lives in this one shared function).
 */
export const OPEN_CARD_EVENT = 'gmatch:open-card'

export function openCardDetail(card: { id: string; card_id?: string | null }): void {
  if (!card.card_id) return
  window.dispatchEvent(new CustomEvent(OPEN_CARD_EVENT, { detail: { cardId: card.card_id } }))
}
```

## Risks, tradeoffs, open questions

- Silent no-op vs. an "open image zoom" redirect on legacy single-clicks: the gallery
  already establishes "no card = no detail modal" and double-click zoom exists on the
  Lobby tile (`onExpandItem`), so the guard matches the house behavior. Add a nicer
  affordance only if the user complains clicks feel dead on legacy items.
- If the 404 URL turns out to be a REAL card id owned by the user (e.g. cashed-out or
  moderated between list-fetch and click), the residual 404 is correct server behavior
  (stale grid); `CardDetailView.tsx:113-116` already surfaces an error state. Verify
  case-by-case with: `bun probe` style signed GET against central, or just reload the
  grid and re-click. Not building cache-busting for that (YAGNI).
- `canonicalCardId` removal is the only deletion; nothing else imports it (verified by
  grep this session). If a sibling agent added a new importer between now and Task 2,
  tsc will fail loudly — re-point it at `card.card_id`.
