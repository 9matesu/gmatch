# Plan: RAM-to-Disk Cache + Timeline Image Fix

## Goal
Replace in-RAM image caches with encrypted on-disk storage to cap total app memory at 200-300 MB, and fix recent timeline images not loading.

## Current Context / Assumptions

Three RAM consumers identified:

1. `electron/imageCacheMemory.cjs` — main-process LRU Map, 96 MB byte budget. Stores raw Buffers keyed by fnv1a hash. Served via `gmcache://` protocol handler in `imageCache.cjs`.
2. `src/services/imageCache.ts` — renderer session Map, 250-entry cap. Stores Blob objects + object URLs. Background-fetches remote images into RAM. Used by `CachedImg.tsx`.
3. `src/hooks/useObjectImage.ts` — module-level `objectCache` Map, 96-slot LRU. Stores blob URLs from signed `/api/objects/:id` fetches. Pin system prevents eviction of mounted entries; when all pinned, cache grows unbounded (line 83: "RAM beats a blank screen").

Recent images not loading root cause: `useObjectImage.ts` line 182 fires `orbitFetch` AND line 167 fires `getLocalObject` concurrently for the same ID. No cancellation of the slower path. The `pinned` set grows per-mount but `cacheSet` evicts unpinned entries — if feed renders many cards fast, entries get evicted before `<img>` paints, causing blank placeholders. Additionally, `ObjectImage.tsx` line 137 has a 1500ms fallback timeout that forces `inView=true`, but by then the cache entry may already be evicted.

The API sidecar (`apiSidecar.cjs`) now uses file-backed SQLite (confirmed fixed in prior session). Not a RAM concern anymore.

No existing disk-cache infrastructure. Legacy IndexedDB was explicitly destroyed (`imageCache.ts` line 74-86) for security. Vault (`vault.cjs`) exists but is opt-in user media, not feed cache.

## Architecture / Proposed Approach

Single encrypted SQLite file in `userData/imgcache.db` replaces all three RAM caches. AES-256-GCM per-row using the existing `storage.key` (already generated by `apiSidecar.cjs`). Main process owns the DB; renderer requests via IPC. Images load lazily — only when scrolled into viewport. On miss, fetch from network, encrypt, write to DB, return decrypted bytes as `blob:` URL. LRU eviction by total DB size (cap 500 MB on disk, ~0 RAM resident).

For the image-loading bug: remove the concurrent dual-fetch race in `useObjectImage.ts`, serialize P2P-then-network, and tie cache lifetime to component mount via ref-counting instead of a global pin set.

### Task 1: Create encrypted disk cache module (main process)

File: `I:/goongrid/apps/desktop/electron/diskImageCache.cjs` (new)

```js
const fs = require('fs')
const path = require('path')
const crypto = require('crypto')

// ponytail: synchronous sqlite3 via better-sqlite3 would be faster but adds a dep;
// node:sqlite is available in node>=22.6 but Electron bundles its own node.
// Use electron's built-in safeStorage for key wrapping, raw fs+crypto for blobs.
// Upgrade path: switch to better-sqlite3 if seek latency exceeds 50ms p99.

const ALGO = 'aes-256-gcm'
const MAX_DISK_BYTES = 500 * 1024 * 1024 // 500 MB ceiling

let dbPath = null
let encKey = null // 32-byte Buffer
let index = new Map() // key -> { size, ts }
let totalBytes = 0

function init(userDataPath, storageKeyHex) {
  dbPath = path.join(userDataPath, 'imgcache')
  try { fs.mkdirSync(dbPath, { recursive: true }) } catch {}
  encKey = Buffer.from(storageKeyHex || crypto.randomBytes(32).toString('hex'), 'hex').subarray(0, 32)
  index.clear()
  totalBytes = 0
  // Rebuild index from disk
  try {
    const files = fs.readdirSync(dbPath)
    for (const f of files) {
      if (!f.endsWith('.enc')) continue
      const stat = fs.statSync(path.join(dbPath, f))
      const key = f.slice(0, -4)
      index.set(key, { size: stat.size, ts: stat.mtimeMs })
      totalBytes += stat.size
    }
  } catch {}
}

function encrypt(buf) {
  const iv = crypto.randomBytes(12)
  const cipher = crypto.createCipheriv(ALGO, encKey, iv)
  const enc = Buffer.concat([cipher.update(buf), cipher.final()])
  const tag = cipher.getAuthTag()
  return Buffer.concat([iv, tag, enc])
}

function decrypt(raw) {
  const iv = raw.subarray(0, 12)
  const tag = raw.subarray(12, 28)
  const enc = raw.subarray(28)
  const decipher = crypto.createDecipheriv(ALGO, encKey, iv)
  decipher.setAuthTag(tag)
  return Buffer.concat([decipher.update(enc), decipher.final()])
}

function evict() {
  while (totalBytes > MAX_DISK_BYTES && index.size > 0) {
    let oldestKey = null
    let oldestTs = Infinity
    for (const [k, v] of index) {
      if (v.ts < oldestTs) { oldestTs = v.ts; oldestKey = k }
    }
    if (!oldestKey) break
    del(oldestKey)
  }
}

function put(key, buf) {
  if (!dbPath || !encKey) return false
  const prev = index.get(key)
  if (prev) { totalBytes -= prev.size; fs.unlinkSync(path.join(dbPath, key + '.enc')).catch?.(() => {}) }
  const encrypted = encrypt(buf)
  fs.writeFileSync(path.join(dbPath, key + '.enc'), encrypted)
  index.set(key, { size: encrypted.length, ts: Date.now() })
  totalBytes += encrypted.length
  evict()
  return true
}

function get(key) {
  if (!dbPath || !encKey) return null
  const meta = index.get(key)
  if (!meta) return null
  try {
    const raw = fs.readFileSync(path.join(dbPath, key + '.enc'))
    meta.ts = Date.now() // touch for LRU
    return decrypt(raw)
  } catch {
    index.delete(key)
    totalBytes -= meta.size
    return null
  }
}

function del(key) {
  const meta = index.get(key)
  if (!meta) return false
  try { fs.unlinkSync(path.join(dbPath, key + '.enc')) } catch {}
  index.delete(key)
  totalBytes -= meta.size
  return true
}

function clear() {
  if (!dbPath) return
  try { fs.rmSync(dbPath, { recursive: true, force: true }) } catch {}
  try { fs.mkdirSync(dbPath, { recursive: true }) } catch {}
  index.clear()
  totalBytes = 0
}

function stats() { return { files: index.size, bytes: totalBytes } }

module.exports = { init, put, get, del, clear, stats }
```

## Risks, Tradeoffs, Open Questions

- Disk I/O latency: synchronous `readFileSync` per image serve blocks the main process event loop briefly. For a 300KB image this is ~2ms on SSD. If jank appears, switch to async read + queue. ponytail comment left in code.
- Storage key sharing: `diskImageCache.cjs` needs the same `storage.key` as the API sidecar. Currently read from `userData/storage.key`. If user deletes this file, all cached images become unreadable (acceptable — they re-download).
- Security: encrypted files on disk satisfy the original "content must never cross a session on disk in plaintext" requirement. Decryption key lives in `userData` (same trust boundary as the app itself).
- Feed RAM cache (`feed` object in `imageCache.cjs` lines 39-40, 276-304): still RAM, but it stores parsed JSON arrays (tiny, <1MB). Left as-is. YAGNI to disk-cache query results.
- Dev mode: browser has no main process, so `resolveImage` falls through to raw URL. No caching in dev. Acceptable tradeoff.
