# ADR-002 — Servers: diretório público + federação de nós

Data: 2026-09-09 · Status: aceito · Plano: `.hermes/plans/2026-09-09_161233-ponytail-encrypted-api-servers.md`

## Decisão

1. **Servidor = full node.** O app já sabe HOSTEAR a API (bundle electron, `server-mode.cjs`) e já sabe CONECTAR como client a um servidor remoto. "Criar um servidor" = modo host + registrar-se no diretório; "entrar" = modo client apontando para o endpoint do host. Nenhum mecanismo novo de transporte.
2. **Diretório fica SÓ no central** (`/api/servers`), com allow-list no gate `SITE_SERVICES`. Contém apenas: id (hash do registro), nome, descrição ≤200 chars, orbitId+pubkey do dono, hint de endpoint, flag `password_required`, timestamps. O central **não vê conteúdo nem usuários** de nenhum servidor — e não pode, porque cada nó é um SQLite independente na máquina do dono.
3. **Dono = admin do próprio nó.** Registro no diretório exige assinatura Ed25519 da identidade do dono. Não criamos um segundo mecanismo de admin: o host do nó já tem a suíte `is_admin` + `admin.ts` + `AdminApp` (PIN-gated); a suíte `is_admin` + `admin.ts` + `AdminApp` (PIN-gated), aberta como **modal** pelo botão **Admin** no HUD do `CommandIsland` (não é rota: `#/admin` foi desregistrado de `ROUTE_VIEWS`); a rota `POST /api/server/password` também aceita o primeiro usuário registrado (host de um nó novo).
4. **Senha de entrada é verificada NO HOST** — scrypt (N=2^15, r=8, p=1) com salt por nó, hash em `SystemMeta`, lockout 5 tentativas / 15 min, nunca no central. Quem passa na verificação entra numa **allowlist persistida no nó** (`server_verified_v1`, chaveada pelo orbitId VERIFICADO POR ASSINATURA — sem token-bearer forjável em header). Membros existentes no momento da ativação são grandfathered por um snapshot `epoch` tirado no `POST /api/server/password`. O handoff cliente (Servers tab → prompt → `gmatch.server.join` no KV local → verify one-shot no boot pós-restart) mantém a senha fora de logs e de URL.
5. **Dashboard/userlist vem do próprio nó** (`GET /api/servers/dashboard`): nome, integrantes (id truncado + display_name + boolean online na janela de 60s já usada pelos hacks), posts 24h. Servidores remotos no diretório NÃO expõem userlist ao central — isso seria conteúdo; a lista aparece somente quando você está conectado àquele nó.

## Consequências / limites honestos

- "Todo player guarda um pedaço do servidor": nesta versão, **não automaticamente**. Disponibilidade = host online. O admin do nó pode exportar/importar a **snapshot do mundo** (JSON de ~54 tabelas de conteúdo em `routes/snapshot.ts`: `GET /api/snapshot` + `POST /api/snapshot/import`, admin-only, allowlist de tabelas de conteúdo — `SystemMeta`, `ServerDirectory`, `Devices`, `Sessions`, `RateLimits`, `AdminAuditLog` etc. são **excluídas por design** para que a snapshot não carregue segredos/transporte do nó). Um sucessor importa o arquivo e assume o mundo. Replicação automática multi-réplica (estilo swan/BT) é projeto de pesquisa à parte — registrado como NÃO-feito.
- "Novo player entra sem transferência → servidor vazio" é o comportamento esperado de um diretório: o conteúdo nunca esteve no central; entra-se no nó do host que já tem os dados, ou num nó vazio recém-criado.
- `endpoint_hint` não resolve NAT: criar servidor atrás de CGNAT permanece não-joinável de fora (a UI avisa; port-forwarding é do usuário).
- Servidor privado com senha: metadados do diretório (nome/dono) são públicos por design — se o dono quer lista privada, é host-and-share-fora-de-band, não diretório.

## Share flows (2026-09-12, onda de release)

- **Codigo do no** (`gmatch://node/...`, `src/utils/nodeMask.ts`): coordenada compartilhavel que o HOST copia (Servers -> Share, no hero ou na linha do diretorio) e o amigo cola (Servers -> Node code). Nao e fronteira de seguranca; carrega host:port e so o `GET /api/servers` autenticado entrega `endpoint_hint`.
- **Prompt de join e in-app** (`PromptDialog.tsx`): Electron nao implementa `window.prompt` (retorna null), entao senha de join e cola-codigo usam dialogos proprios.
- **`owner_name` na linha do diretorio** (migracao 050): handle reportado pelo HOST, clampado a 40; classe best-effort identica a `user_count`/`online_count` (um host pode mentir sobre o proprio nome). O payload de registro envia `owner_name`; a linha do browser **nao** o renderiza (nunca `by <nome>` — `ServersView.mask.test.ts` falha se `owner_name` voltar ao JSX).
- **Vivacidade**: o heartbeat regrava a linha a cada 15min e agora bootstrapa o registro para instalacoes em modo host sem Create no jogo (troca via Settings -> Server). Linhas morrem em 24h de silencio; a UI mostra seen Xm ago.
- **Alcance**: o codigo carrega endereco LAN; join entre redes diferentes segue dependendo de port-forwarding (limite ja documentado acima para `endpoint_hint`).

## Apresentacao do browser (revisao da superficie, 1.5.6)

Sem mudanca de protocolo: e a mesma federacao, com uma superficie que diz a verdade.

- **Uma lista, uma linha por servidor.** Um no que hospeda um mundo E um servidor, seja de quem for, incluindo o que roda **nesta maquina**. Ele aparece uma unica vez, na posicao normal da lista, chaveado pelo endereco (`serverKey` em `directoryMerge.ts`), de modo que o registro do diretorio e a linha sintetica colapsam num so item. Nunca se deduplica por nome de exibicao: dois servidores diferentes podem chamar-se igual.
- **Courier nao e destino.** O `onrender.com` (e qualquer no que hospede so mail/turn/diretorio) e infraestrutura: sai da lista, junto com o badge de transporte e a chamada de presenca. O mundo publico `gmatch public` (endereco `gmatch.fly.dev`, no completo) e embutido na lista com probe proprio de saude; aparece primeiro, e clicavel como qualquer destino e fica offline se o probe falhar.
- **Um cabecalho, uma acao primaria.** `Servers` + `+ Add server` (o unico preenchido) + busca discreta + refresh discreto; a engrenagem de diretorio guarda o endereco central, o painel admin e o chaveamento de dev. Sumiram: o card do mundo atual, as secoes `Destinations`/`Hosted servers`, a secao permanente de grupos locais, o aviso de privacidade, o toolbar de ordenacao, o filtro de senha e os botoes de linha duplicados. O drill-in do hub entra pelo menu da propria linha (`Open dashboard`).
- **A linha** (`WorldRow.tsx`): ponto de estado + nome + no maximo UMA etiqueta quieta (`P2P`, so para o no desta maquina) + `Current`/`Connecting`/`Unavailable`; segunda linha com `descricao · dominio · listed Nm ago`, sem IP cru, sem transporte, sem diagnostico. Clicar a linha entra/troca; a linha atual e inerte e nao reconecta. Um unico menu de tres pontos (`Open dashboard`, `Server settings`, privacidade, `Copy code`, `unregister`, `Delete / Forget`) — so as operacoes que a arquitetura atual sustenta.
- **Estados honestos**: `Current` / `Connecting` / `Unavailable`. Um numero sem dado real por tras nao vira `— / —`; um fetch falho do diretorio mantem o que ja se conhece e mostra retry; uma linha `Unavailable` nao se oferece como pronta para conectar.
- **Add server** (`AddWorldDialog.tsx`, sobre o `Modal` existente) abre em dois passos — `Join with code` ou `Host a server` — com uma acao primaria por passo e o formulario de host (estado e restart flow) injetado pela view. Codigo invalido mostra erro no proprio campo e preserva o texto.
- **Grupos locais** (rotulo **so deste dispositivo**) sairam da lista: um rotulo nao e servidor nem destino. Ficam atras de um link discreto no rodape (`GroupsDialog.tsx`): listar, criar, `Forget`. `Local groups` nao cria rede alguma.
- `create`/`join`/`switchTo`/`joinByCode`/`leave`/`switchClientWorld`/`shareServer`/`unregister` continuam intocados; o polling de 30s segue silencioso e o guard de conexao (`connectingId`) impede joins concorrentes.
- Docs do que a tela promete: `docs/BROWSER-PERF.md` §10; contrato de comportamento em `ServersView.test.tsx` + `GroupsDialog.test.tsx` + `directoryMerge.test.ts` (identidade) e paridade de JSX em `ServersView.mask.test.ts` (sobre `ServersView.tsx` + `WorldRow.tsx`).
